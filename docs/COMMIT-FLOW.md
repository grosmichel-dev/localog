# 커밋 흐름 (COMMIT-FLOW)

무엇이든 main에 들어가는 경로는 하나입니다: **브랜치 → PR → CI 초록 → 병합.**

## 1. 콘텐츠 변경 (content/ · originals/ · assets/)

혼자여도 예외 없습니다. 사람의 다짐이 아니라 CI가 개인정보 유출을 막는 마지막 그물이기 때문입니다.

1. 작업 브랜치 생성 (예: `add/2026-05-14-청년창업공고`)
2. 옵시디언에서 작성 → 원문 대조 → 마스킹 → 서명 필드 기입 (`docs/SCREENING_SOP.md`)
3. 푸시 후 PR 생성 → PR 템플릿 체크박스 작성
4. 필수 CI(게이트 검사·프론트매터 검증·개인정보 린트) 초록 확인
5. 병합
   - 솔로 구간: 필수 승인 0, 셀프 병합 허용. 단, CI 초록일 때만.
   - 2번째 커밋터 합류 후: **리뷰어 1인 이상 승인, 작성자 ≠ 리뷰어.**

## 2. 인프라 변경 (tools/ · 워크플로 · 설정 · 문서)

- 같은 경로(브랜치 → PR → CI 초록)를 거치되, 솔로 셀프 병합을 허용합니다.

## 3. 브랜치 보호 설정 (1일차부터, owner가 GitHub 설정에서 직접)

main 브랜치에 다음을 켭니다. 이 설정이 있어야 솔로라도 "실수로 main에 직접 푸시"가 기술적으로 차단됩니다.

- [ ] Require a pull request before merging (병합 전 PR 필수)
- [ ] Require status checks to pass (필수 CI 지정)
- [ ] Block force pushes (강제 푸시 차단) + 브랜치 삭제 차단
- [ ] 가능하면 admin bypass 비활성화 ("Do not allow bypassing the above settings")
- [ ] 필수 승인 수: 솔로 = 0 → 2번째 커밋터 합류 시 1로 상향 (작성자 ≠ 리뷰어)

owner가 이 설정 자체를 끌 수 있다는 한계는 `GOVERNANCE.md` 7절에 "수용된 admin 잔여 리스크"로 기록돼 있습니다.

## 4. 인테이크 대기함 점검 (주간 수기 폴백)

자동 SLA 알림이 없는 솔로 구간에는 이렇게 합니다.

- 매주 정한 요일에 (작성 필요: 요일 지정) 구글폼 응답 시트와 로컬 `inbox/`를 확인합니다.
- 5영업일 넘게 대기 중인 항목부터 처리합니다.
- 처리할 수 없는 항목(HWP 전용, 출처 불명 등)은 시트에 사유를 남기고 종결합니다.
